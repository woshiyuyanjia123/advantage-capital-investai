# 云端同步：设备令牌 + 基于历史表的增量拉取，推送预留

未来会部署云服务器，多个办公室的桌面应用、报表与备份程序需要从它获取数据。我们决定：

- **身份**：同步客户端用设备令牌（`iai_…`，只存哈希、可吊销、有有效期），令牌代表一个具体人员，数据权限等同此人；令牌只能调用 `sync.*` 接口。不另设「同步超级账号」，避免同步通道成为绕过四层权限的后门。
- **变更源**：直接用已有的 `history` 表（每次写入一条、自增序号）作为变更流，不新建变更日志，也不修改写入路径（ADR 0001）。拉取时按记录去重、返回当前状态，并用与界面相同的投影脱敏；看不到的记录以 `removed` 返回，覆盖删除和权限收回两种情况。
- **方向**：当前只实现云端 → 客户端拉取。推送（`sync.push`）先返回 501：多点写入需要冲突处理（默认以云端为准）和流程状态的一致性校验（推进、表决不能在两边各做一次），在云服务器真正上线、明确多点写入场景后再实现。
- **会话**：云端多人使用后，会话从进程内存移到 SQLite 的 `sessions` 表（只存 sid 哈希），服务重启不掉线，并支持闲置超时、管理员强制退出。

考虑过的其他方案：直接同步 SQLite 文件（会绕过权限、无法合并）；整库导出导入（无增量、无脱敏）；CRDT 双向同步（对审批、表决这类必须单点决定的流程不适用）。
